# Software Architect Training

**A hands-on learning portfolio by Thomas Gomrée**

Documenting my journey through C#/.NET, ASP.NET Core, software architecture, design patterns, cloud technologies, DevOps, testing and practical projects.

> **Current phase — preparation / onboarding (November 2026).** This repository is being structured before the first course modules. Planned topics are not presented as completed work.

## Purpose

This public repository has two complementary roles:

1. **Learning laboratory:** small original exercises and focused experiments to understand how technologies and architectural patterns work.
2. **Professional showcase:** a curated set of reproducible projects, diagrams, architecture decisions and test evidence that demonstrates skills acquired over time.

I value the reasoning behind the implementation: requirements, choices, alternatives, trade-offs, validation and lessons learned — not just source code volume.

This personal work accompanies the [AI-Driven Software Architect programme at Technofutur TIC](https://technofuturtic.be/catalogue/action/ai-driven-software-architect-09-11-2026-11813), starting on **9 November 2026**.

## What I intend to demonstrate

The learning areas below are **goals, not self-assessed proficiency levels**.

- **Software development:** C#, object-oriented design, .NET and ASP.NET Core.
- **Data and integration:** SQL modeling, EF Core, Dapper, APIs and external services.
- **Software architecture:** separation of concerns, dependency inversion, patterns, UML and architectural decision records.
- **Quality and security:** testing, maintainability, authorization, threat awareness and performance.
- **Delivery and cloud:** Git, DevOps, containerization, deployment and operational trade-offs.
- **Communication:** explaining decisions, constraints and results clearly.

See the [public evidence index](docs/showcase.md) for what has actually been demonstrated.

## Documentation standard

Substantial examples should provide:

1. A clear problem statement and constraints.
2. A concise architecture overview and important trade-offs.
3. Instructions for running and testing the example.
4. Actual test or validation evidence, where available.
5. Known limitations and potential improvements.

Architectural decisions can use the [ADR template](docs/adr/0000-template.md).

## Public repository policy
